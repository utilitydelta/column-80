# Architecture

Start here. This is the root map: what the system is, what it refuses to be, the invariants that hold everywhere, and a link per subsystem. Depth is opt-in via the links.

## What this is

A VS Code extension for the human coding flow: the human implements the system, holds the context in their head, and expresses design directly in code, but does not type character by character. Two model paths. FIM is always local; function generation is local by default with an optional cloud frontier backend the user turns on deliberately:

1. **FIM tab-completion**: ghost text from a small base model (`qwen2.5-coder:1.5b-base`), in code and only in code - the languages carrying an oracle or an extractor, widened by one setting. Always local, no cloud path.
2. **Per-function generation**: cursor in a function, generate or regenerate the body from a large instruct model (`qwen3-coder:30b`, or a 14b fallback on smaller hardware) by default. A user who wants more capability and accepts sending their code out can instead point this one path at a cloud frontier model, or at their own installed Claude Code CLI on a subscription (`fnGenProvider`). The unit of generation is the function. Never the file, never the module.

Around those two paths: user-curated context blocks (the human selects everything the model sees), a compiler oracle that checks accepted generations with the language's own toolchain and can run gated cross-model repair, language-server surface injection that feeds the model the real API the compiler says it got wrong (the v2 thesis), and hardware tier auto-select with the VRAM carve that keeps both models GPU-resident on a 16GB card.

Both mechanisms are language-pluggable behind two seams: `oracleFor(languageId)` picks the compiler strategy, `extractorFor(languageId)` picks the surface extractor. Four languages ride them today: Rust (cargo check + rust-analyzer), TypeScript/JavaScript (tsc + the TS language service, v9), C# (dotnet build + the Roslyn language server, v10), and Python (pyright + Pylance, v11). A language without a registered oracle or extractor degrades honestly: no check, no injection, never a guess.

The design principle behind every gesture: this is a flow-state tool for a developer engaged in system-2 thinking. The human designs; the tool removes typing. No gesture may break the design thread. If a feature makes the developer manage the tool instead of the system they are designing, it fails, regardless of capability. Cognitive surrender is the failure mode designed against.

## What this is NOT (v1)

Reject work that pushes toward any of these:

- No agent mode.
- No MCP.
- No automatic context retrieval, repo indexing, or relevance ranking. The human selects everything the model sees.
- No chat panel.
- No telemetry.
- No automatic or hidden cloud calls. The default install is local-only and makes no cloud call ever. The exceptions are opt-in and narrow, and both are *function generation* only: a user may set `fnGenProvider` to a cloud frontier model with an API key, or to `claude-code`, which runs their installed Claude Code CLI headless and bills their Claude subscription instead of a key. Both are off by default, both are the only paths that can leave the machine, and both are loud about doing so. FIM is never cloud, and nothing else in the extension (context, oracle, injection, catalog) ever reaches a cloud API. Everything below about the offline default holds unchanged when neither is chosen.
- No network dependency at runtime in the default (local) configuration. After the one-time model pull and the normal `cargo fetch` of dependencies, the tool runs fully offline. Every worked example, signature, and catalog entry is sourced from what is already on disk (the local crate source under `~/.cargo/registry/src/`, read through the user's rust-analyzer). Nothing in a generation, repair, or injection path reaches the network on the local path. See the offline invariant below.

Reserved for later versions, deliberately not designed here: context-aware delta generation with a bounded refine loop, richer execution oracles (test-failure-as-repair-signal, coverage), further oracle languages behind the existing seams (Go is scouted and parked), the macOS/Apple Silicon and non-NVIDIA ecosystem, and constrained decoding/masking against a llama.cpp backend. The full forward plan lives in [docs/roadmap.md](docs/roadmap.md).

## Product invariants

These were the build's falsification bars and remain the product's testable properties. Breaking any one is a broken product, not a regression to triage.

1. **FIM latency**: warm TTFT under 200ms at a realistic 2-4K character context on the reference box (RTX 5080; measured floor 103ms TTFT / 140ms total).
2. **Function boundary**: generation never modifies bytes outside the target function's span. Enforced by splice arithmetic plus a byte-compare oracle, producer guards, and accept-path staleness guards. See [fn-generation](docs/architecture/fn-generation.md).
3. **Context trust**: a context block the user removed never reaches a prompt. Zero tolerance; this is a trust feature. A block is a live RANGE over a live document, not a frozen copy of text: at generate time the model gets what those lines say NOW, so a block over a function you are still writing carries the implementation you just typed into it. The claim is *the lines you chose, as they read now* (session-v33 reversed the older *the snapshot you saw is the snapshot the model gets*; `docs/supersessions.md` S4). Nothing is ever added automatically, order in the panel is order in the prompt, and a block an edit destroyed goes red, toasts, and is excluded from the generation rather than silently sent. What this trades away is reproducibility of the exact bytes: two generations minutes apart can differ because you typed in between, and the panel rendering live text is what keeps that inspectable. See [context-blocks](docs/architecture/context-blocks.md).
4. **Repair discipline**: the repair loop never runs more than 2 rounds, and never attempts repair from an assertion failure. Both structural, not conventional. See [compiler-oracle](docs/architecture/compiler-oracle.md).
5. **The carve**: on the reference 16GB config, both models stay resident and a mixed FIM/fn-gen alternation triggers zero evictions, with the FIM latency bar holding during alternation. See [hardware-tiers](docs/architecture/hardware-tiers.md).

Structural invariants that hold system-wide:

- **Prompt identity (v1 core, unchanged when injection is off)**: with `compilerDirectedInjection` off, the fn-gen prompt is exactly signature + doc comment + the user's ordered context blocks, and nothing else. No file prefix/suffix, no imports, no repo content, no system message, no metadata. The assembler is byte-identical to v1 when no surface is injected, and the frozen prompt-identity oracles pin that. Identity is over the assembler's INPUTS, not over time: the blocks are live ranges (invariant 3), so the same cursor and the same panel can assemble different bytes tomorrow because the human edited the lines in between.
- **Prompt identity (v2, injection on, the default)**: v2 revises the identity deliberately, from *human-selects-everything* to *human-can-veto*. The prompt MAY also carry API surface the tool resolved from the user's running rust-analyzer: the real crate example or signatures on a compile-time hallucination, and the signature/doc-named types' surface at round 1. Every injected block is a visible, labelled section in the previewed prompt, is inspectable after the fact on the evidence channel (`[repair] surface injected …`, `[fngen] pre-fill …`), degrades to the v1 prompt when rust-analyzer resolves nothing (never a silent guess), and is switched off entirely by one setting. The injection is defaulted and always overridable; it is never hidden. Imports are not injected as prose - a missing-but-resolvable name is qualified in place (`fastbloom::BloomFilter`) through the same consent gate, so even the v2 prompt still never carries a `use` line the human did not write.
- **Consented document writes, no silent insertion**: three, and only three, code paths write to a document, and all three are non-silent. (1) `ProposalPresenter.present` (src/vscode/fnGen.ts) — the preview-and-confirm diff gate every generation and repair goes through. (2) The TDD test gesture (`column80.generateTests`) inserts the blank-value test module as a VS Code *snippet* via `editor.insertSnippet`, because a read-only diff tab cannot host the blank-value tabstop entry the human Tabs through and types into. This is a deliberate second write path: it fires only on an explicit command, writes a scaffold whose expected values are empty holes the human must fill (the model's guessed value is never inserted), and emits its evidence line before the write. (3) The TDD test gesture CREATES the test file when it does not exist yet, which neither other path can do — only Rust puts its tests in the file under test, and Go, TypeScript, Python and C# all need a sibling or a project file (`docs/supersessions.md` S3, human-ratified). It is not exempt from consent: the whole new file is previewed as a diff against empty through the same presenter machinery, with the expected values blank in the preview as well as in the buffer; reject writes nothing and leaves no file behind; and it creates a test FILE only, never a test project, a config, a manifest or a package install. The invariant all three preserve is *no silent model write*, not *one literal function*. Everything outside the TDD gesture still writes exclusively through `ProposalPresenter.present`.
- **Never auto-pull**: nothing model-shaped happens silently. Model downloads happen only after an explicit human ratify click, and the ratify evidence line lands before the network request starts.
- **Offline after setup (local path), one opt-in exit (cloud fn-gen)**: on the default local path the only network access the tool ever makes is the ratified model pull and whatever `cargo fetch` already did to put dependencies on disk. Past that line the tool is fully offline. This is the student persona's whole reason for existing (cloud tiers were frozen; local is the only thing they control), so an *unrequested* runtime network call is a broken product, not a slow one. The single deliberate exit is the cloud fn-gen backend: when the user sets `fnGenProvider` to a cloud provider, the assembled function-generation prompt (signature, doc comment, selected context, injected crate surface) is sent to that provider, and nothing else is. It serves a different user than the student and is never on by default.

  The `claude-code` provider is the same exit through a different door: instead of an API key and an endpoint, it spawns the user's own `claude` CLI headless (`claude -p --output-format json --strict-mcp-config`) with the assembled prompt on stdin, and billing rides their Claude subscription. Three properties of that arrangement are load-bearing enough to state here. It is spawned in a product-owned empty directory under the extension's global storage, NEVER the user's workspace, because spawning in the workspace would silently pull their `CLAUDE.md`, their auto-memory and their project MCP servers into a generation the context panel never showed - a human-curates-everything violation. `--strict-mcp-config` is mandatory on every spawn for the same reason, since user-scope MCP servers otherwise attach in any directory. And what the neutral directory does NOT buy, stated plainly: the CLI's own agent harness (system prompt, tool definitions, settings) plus any global `~/.claude` context loads on every call, because that is how the subscription authenticates. Most of that weight was the CLI's built-in tool definitions, so the spawn passes `--tools ""`: a prompt-to-text generation can never use Read, Write or Bash, and the user should not spend subscription quota on their definitions. Measured on claude 2.1.224, same prompt and byte-identical generated code, 23,217 tokens of input context became 3,471. It also makes the agentic-reply refusal structural rather than detected, since a model with no tools cannot take a second turn. FIM never uses this path - a 5-15s round trip has no business on a keystroke, and the CLI's transport has no infill.

  One known limitation of the `claude-code` provider, measured rather than assumed: cancelling a generation kills the `claude` process but not its process group, so a tool subprocess the CLI had already spawned outlives the cancel and runs to completion. A process-group kill is not portable to Windows, so the orphan is accepted and recorded rather than half-fixed.

  Both off-machine paths cache the user's context blocks, because this product re-sends the same blocks on every generation and pays for them every time. On `anthropic` that is one `cache_control` breakpoint after the blocks, at a one-hour TTL, over a native Messages transport - which is why that one provider no longer rides the shared OpenAI-compatible client. On `claude-code` it cannot be a marker at all: the CLI places its own breakpoint at the END of the user turn, so a changed signature invalidates the whole prompt in front of it. There the blocks go out as their own turn and each generation forks off that checkpoint with `--resume --fork-session`. **The checkpoint is keyed on a hash of the resolved block bytes, and that is a correctness rule rather than a cost one**: blocks are read live, so keying on ids or paths would let a developer edit a pinned range and be served the old text from cache while believing the model saw the new - the frozen-snapshot behaviour session-v33 deliberately reversed, smuggled back in through a cache. Caching never fails a round: a missing, expired or unforkable checkpoint degrades to a whole-prompt call and says so on the evidence line. And nothing is warmed speculatively, in the background, or on idle, on any backend - the extra turn happens on the user's first generation against a block set and nowhere else, because pinning a block is not a request for a model call.

  Everything that is not the fn-gen model call stays local unconditionally: surface injection reads local crate source through rust-analyzer, never `docs.rs` or any registry API; the catalog reads `cargo metadata`, which is local; FIM is local; no path resolves an example, signature, or type over the network. A path that reaches the internet to source surface still fails the gate regardless of quality.
- **This extension publishes no diagnostics**: the compiler's own output from a real check run (rustc JSON, tsc text, dotnet SARIF, pyright JSON) is the oracle's input of record, and nothing reads `vscode.languages.getDiagnostics` back into the loop. Nothing writes one either. Owning a diagnostic means owning its lifecycle, including clearing it when the human fixes the code by hand, and the language server already does that for the same errors. The check speaks through the edit-site annotation and the output channel; the Problems panel belongs to the compiler.
- **Fail-closed tier gating**: every model-call entry point consults the tier gate. An unresolved or disabled tier blocks generation with an honest message; a failed hardware probe lands on the FIM-only tier, never an optimistic guess. The gate is not the only layer, because a gate is only as good as the call sites that remember to ask it: a disabled service is built with a transport that rejects (`inertFnGenService`, `src/vscode/fnGen.ts:1294`) on every arm, so a gesture that forgets the gate still cannot reach a host the build declared dead. Tighten Doc Comment was exactly that gesture until session-v56, and it was handed a live transport with no gate at all.
- **Evidence discipline**: every meaningful path emits a line on the output channel (`[fim]` `[fngen]` `[ctx]` `[oracle]` `[repair]` `[carve]`). A path is finished when it emits evidence, not when it compiles.

Testing discipline, carried from the build: the `test/blind*.test.cjs` files are frozen black-box contract oracles written from the subsystem contracts before implementation. They are never edited to make an implementation pass. See [vscode-layer](docs/architecture/vscode-layer.md) for the harness shape.
